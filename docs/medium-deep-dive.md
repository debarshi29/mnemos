# Giving Your AI Assistant a Memory It Doesn't Just Forget: Inside mnemos

*How a small, self-hosted memory layer treats forgetting, contradiction, and belief-revision as first-class design problems — instead of pretending they don't exist.*

---

Every hosted AI assistant claims to "remember" you. In practice, that memory is a black box: you can't see what it stored, why it chose to surface a fact, or what happened the day you told it something that contradicted what it already believed. It either silently overwrites, silently ignores, or — worst — silently hallucinates a merge of both.

I wanted to see what it would look like if none of that were hidden. That's **mnemos** — a self-hosted memory system for AI assistants where every fact is inspectable, every contradiction is resolved by an explicit, auditable policy, and nothing is ever deleted without leaving a trace.

This isn't a wrapper around a vector database. It's an opinionated pipeline that turns raw conversation into structured, decaying, provenance-tracked belief — and it's small enough to read end to end in an afternoon.

## The problem with "just embed everything"

The naive approach to AI memory is: embed every message, store it in a vector DB, retrieve the top-k nearest neighbors at query time. This works until it doesn't:

- **Nothing decays.** A fact from six months ago ranks exactly as high as one from this morning, provided the embeddings are similar enough.
- **Nothing resolves.** If you told it you were a "junior engineer" in March and a "senior engineer" in October, both facts sit in the index with equal standing, and retrieval just returns whichever one is textually closer to the query.
- **Nothing is auditable.** When the assistant says something wrong, there's no way to trace *which* stored fact it came from, or *which conversation* produced that fact.

mnemos exists because all three of those are solvable with surprisingly little machinery — you just have to decide, up front, what "forgetting" and "changing your mind" mean for a system that isn't human.

## Three tiers, one pipeline

Everything in mnemos starts life as an **Episode** — a raw, unprocessed turn of conversation or an ingested document. Episodes are cheap and disposable in spirit, even though they're never actually deleted.

Periodically (or after every session, depending on config), a background process I call the **sleep cycle** runs over a batch of episodes and distills them into **Facts** — confidence-weighted, typed, declarative statements like *"the user is learning LangGraph"* or *"the user prefers terse code review comments."* Facts are the unit of long-term memory: embedded, indexed, retrievable, and subject to decay.

A third tier, **GoalFacts**, holds phased roadmaps generated by a research-backed planner — but the interesting design decisions all live in the Fact layer, so that's where this piece stays.

```
Episode (raw turn)
      │
      ▼
┌─────────────────────────────────┐
│         Sleep Cycle             │
│  extract → dedupe → contradict  │
│         → prune                 │
└─────────────────────────────────┘
      │
      ▼
Fact (confidence-weighted, typed, decaying)
```

The sleep cycle is a four-node LangGraph, compiled once and run as a linear pipeline — no branching, no retries, no cleverness. Each node has exactly one job:

**Extract.** An LLM call turns each raw episode into a list of candidate facts, each tagged as one of six types (`preference`, `status`, `event`, `skill`, `goal`, `other`). A parse failure on one episode is swallowed and skipped — one malformed response doesn't sink the batch.

**Dedupe.** Every candidate is embedded and compared against the existing fact base by cosine similarity. Above a 0.92 threshold, it's treated as a *re-observation*, not a new fact — which triggers the interesting part.

**Contradict.** Below the dedupe threshold but above a looser 0.60 similarity threshold, two facts are topically related enough to be worth asking an LLM: *do these actually conflict, or do they just sound similar?* Only genuine conflicts get resolved.

**Prune.** Facts whose confidence has decayed below a floor are soft-deleted.

Two different similarity thresholds, doing two different jobs, is the detail that makes this pipeline actually work: deduplication needs near-verbatim restatement (0.92), while contradiction detection only needs topical relatedness before an LLM adjudicates (0.60). Conflate the two and you either miss real contradictions or flag every loosely related fact as a conflict.

## Confidence isn't binary — it's an exponential moving average

When a fact is re-observed (the "dedupe" case above), its confidence doesn't just reset to 1.0. It updates as an EMA:

```
new_confidence = w · 1.0 + (1 − w) · old_confidence
```

with `w = 0.7` by default. Each re-observation pulls confidence toward certainty without ever fully discarding history. Say something once, and it's provisionally believed. Say it five times across five sessions, and its confidence compounds toward 1.0 — the same way repeated evidence should behave.

## Retrieval is a race between relevance and time

This is the formula that made the whole project feel worth building. At query time, a candidate fact's ranking score isn't just cosine similarity — it's similarity discounted by an exponential decay over the fact's age:

```
score = cosine_similarity(query, fact) × e^(−λ · age_days)

where λ = ln(2) / half_life_days
```

With a 30-day half-life (the default), a fact halves in retrieval weight every month, *regardless of how semantically perfect the match is*. A fact from a year ago needs to be dramatically more relevant than a fact from yesterday to win the same retrieval slot. This is forgetting-as-compounding-decay instead of forgetting-as-hard-cutoff — and it's the single mechanism that keeps a long-lived memory store from becoming a junk drawer of stale preferences.

Implementation-wise, this means over-fetching from the vector store (3× the requested top-k) and re-ranking by decayed score in application code, since the vector index itself only knows about raw similarity. A fact that's a near-perfect match but six months stale needs the chance to be pulled into the candidate pool before decay pushes it back down — over-fetching is what buys that chance.

## Contradiction is a policy decision, not a bug

Here's the part that most memory systems don't even attempt: what happens when two beliefs genuinely conflict?

mnemos treats it as an explicit precedence chain:

1. **Higher confidence wins.** If one fact has been reinforced more than the other, it wins outright.
2. **Tie on confidence → more recent wins.** Ties are broken by `last_seen`.
3. **True tie (equal confidence *and* equal recency) → neither wins.** Both facts are flagged and kept side by side, visible in the UI, waiting for a human (or a future observation) to resolve the ambiguity.

The loser in cases 1 and 2 is never deleted. It's marked `superseded_by = <winner's ID>` — a soft supersession that keeps the fact fully queryable and its provenance chain intact forever. Ask mnemos "why do you believe X" a year from now, and it can still show you the fact that used to hold that position, and why it lost.

This is the design principle that everything else in the system serves: **no fact is ever physically deleted.** Pruning by confidence floor and losing a contradiction both work the same way — soft-delete, provenance preserved. The result is that "why does the assistant believe this" and "why did it stop believing this" are both answerable questions, indefinitely, not just for the current live state of memory.

## Wiring it into an actual assistant

None of this matters if it stays a research toy, so mnemos exposes itself two ways:

- A REST API (`/chat`, `/chat/stream`, `/memory/*`, `/plan`) backing a React frontend with a chat panel, a memory inspector (click any fact, see its full provenance chain), a Kanban-style roadmap board, and a consolidation-run timeline.
- A **FastMCP server** — eight tools (`remember`, `recall`, `get_provenance`, `consolidate`, `list_facts`, `plan_learning_roadmap`, `ingest_file`, `ingest_github`) and two resources, so the same memory layer plugs directly into Claude Desktop or Cursor over stdio or HTTP/SSE.

That second part is what makes it more than a demo: the exact same consolidation pipeline, decay-ranked retrieval, and contradiction resolution that powers the bundled chat UI is available as first-class tools inside a general-purpose coding assistant, with zero code duplication between the two surfaces beyond the storage layer itself.

## What this generalizes to

The reference implementation is a learning copilot — it plans roadmaps, ingests papers and repos, and remembers what you've studied. But the memory layer doesn't know anything about learning. Swap the system prompt and the exact same pipeline becomes:

- A **research memory** tracking hypotheses and findings across sessions
- A **personal CRM** remembering people, relationships, and context
- A **decision log** with full reasoning trails behind architectural calls
- A **stakeholder memory** — who cares about what, what was promised, what's still open

The thesis isn't "AI assistant for learning." It's "memory that decays, resolves contradictions explicitly, and never lies about its own history" — as a reusable layer underneath any domain.
